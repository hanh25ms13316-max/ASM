0. Link to Assignment 1

Problem statement (recap). Every week, score the dropout risk of every enrolled student at BTEC FPT British College (assumed 12,000 students, three 15-week semesters per year) at least 8 weeks before the semester ends. Tier A (top 10 % risk) goes to academic advisors for personal counselling; Tier B (top 10–25 %) goes to the student care team for check-in calls. Business target: reduce annual dropout from 8 % to 6.5 %.

Architecture (recap). Two pipelines share one feature module: a training pipeline runs each semester or on drift; a weekly batch scoring pipeline runs every Sunday. Components: nightly extraction → data validation → pseudonymised warehouse → feature computation → training with MLflow tracking → quality gate + human approval → model registry → batch scoring → advisor/care-team web app; monitoring for pipeline health, drift and fairness; fallback rule B2 when data is invalid.

Refinements after Sessions 3–5.

  • Proxy dataset. No real college data is available, so experiments use the public UCI dataset (4,424 students, 36 attributes, 32.1 % dropout). It has no weekly features, so the feature groups "enrolment / semester 1 / semester 2" simulate predicting earlier or later.
  • Split strategy. The dataset has no enrolment date, so a stratified split replaces the time-based split of Assignment 1; production data will return to a semester-based split.
  • Selection rule as code. Trade-off 5.1 of Assignment 1 ("choose gradient boosting only if its PR-AUC beats logistic regression by ≥ 0.02") is now the function select_model, parameterised in params.yaml.
  • Additions. Cross-validated PR-AUC with standard deviation to separate real differences from noise; a previous-champion alias for one-step rollback; PSI drift detection inside the scoring DAG.

1.3 Design rationale

  • Structure. Each stage has one responsibility and an explicit input/output artefact, so failures are localised and a single stage can be re-run. Validation comes first because bad data that slips through silently corrupts every later stage.
  • Modularity and reuse. Every stage is a plain, typed function in the dropout package that exchanges file paths or objects and has no Airflow dependency; the same functions are called by the experiment script, the DAGs and the unit tests. EngineeredFeatures lives inside the scikit-learn pipeline stored in MLflow, so scoring cannot compute features differently from training (no training-serving skew). A new algorithm is one branch in build_estimator; a new experiment is one line in MATRIX.
  • Error handling and recovery. (1) Invalid data → stop and score with fallback rule B2 so advisors still receive a list; (2) transient errors → Airflow retries twice with exponential back-off; (3) candidate fails the gate → keep the current champion and log the reasons; (4) a bad model in production → move the champion alias back to previous-champion without rebuilding; (5) dated snapshots make every task idempotent and re-runnable.
  • Scalability. Scoring 4,424 students takes under one second and grows linearly; for 12,000–50,000 students scoring can be partitioned by programme and run in parallel. The most expensive step, hyperparameter search (21 s for E07), runs once per semester and can be scaled with n_jobs or Optuna. Switching MLFLOW_TRACKING_URI from SQLite to PostgreSQL + MinIO supports multiple users with no code change.

2.5 Analysis of patterns and trade-offs

  • ML clearly beats the rule. E01 reaches PR-AUC 0.728 while ML models with full features reach 0.871–0.878; Recall@25 % rises from 0.613 to about 0.69. This confirms the "why ML" argument of Assignment 1.
  • Among ML models, differences are within noise. E02–E09 differ by at most 0.007 validation PR-AUC, while CV standard deviations are 0.011–0.018. The best validation model, E09 (0.878), beats logistic regression E02 by only 0.0036. On CV, tuned XGBoost (E07, 0.881) leads E02 (0.871) by about 0.01, still less than one SD. With small tabular data and near-linear academic signals, complex models have little room to win.
  • Ranking vs. calibration. Class weighting does not improve PR-AUC but damages probabilities: ECE rises from 0.023 (E02) to 0.083 (E03); XGBoost with scale_pos_weight (E06) has ECE 0.060. Top-k lists only need ranking, so reweighting brings cost without benefit.
  • SMOTE and isotonic calibration do not pay off. E08 has the highest CV PR-AUC (0.882) but no validation gain and adds synthetic data. E09 has ECE 0.042, worse than uncalibrated E07 (0.020): XGBoost with log-loss is already well calibrated and isotonic fitting on ~530-sample folds is noisy. Calibration should be added only when measured to help.
  • Early detection vs. accuracy (trade-off 5.5 of Assignment 1). Enrolment data only (E10): PR-AUC 0.737, close to the rule; with semester 1 (E11): 0.855; with semester 2 (E07): 0.877. Most signal arrives with the first academic results, supporting weekly scoring whose confidence grows once interim assessments exist.
  • Privacy vs. accuracy (trade-off 5.4). Removing the two financial features (E12) lowers PR-AUC by 0.035 and raises the fairness gap to 0.127, above the limit. Fee status is an important, legitimate signal: keep it, but protect it (pseudonymisation, role-based access, no amounts shown to callers).
  • Fairness. Random forest (E04, gap 0.113) and E12 exceed 0.10 and are excluded automatically, although E04 has a competitive PR-AUC; ranking by PR-AUC alone would have hidden this.
  • Cost. E07 needs 21.3 s for tuning versus 0.20 s for E02; at this scale cost does not decide.

2.6 Recommendation

Select E02: logistic regression, no rebalancing, full feature set. The best PR-AUC model (E09) is only 0.0036 ahead, far below the 0.02 margin set in Assignment 1. E02 is directly interpretable for advisors (coefficients show which factors raise risk), well calibrated (ECE 0.023), within the fairness limit (gap 0.077) and trains instantly. select_model reached this decision automatically. It should be re-evaluated when real weekly features exist, because non-linear interactions (e.g. rising absence and overdue fees) may let it clear the 0.02 margin.

3.4 Operational considerations

  • Failure handling. Two retries with exponential back-off starting at 10 minutes; 1-hour execution timeout per task (3 hours for training). Invalid data does not fail the DAG but branches to the fallback rule. max_active_runs=1 prevents overlapping runs; dated inputs/outputs make every task idempotent. Validation failure in the training DAG stops the run, so the current champion stays in place.
  • Alerting. on_failure_callback e-mails the data team with the task and log link. SLAs (1 h for extraction, 4 h for lists) raise SLA-miss alerts. Fallback activations and drift-triggered retraining are logged and reported.
  • Monitoring. Airflow UI (durations, success rate); MLflow (metrics per model version); weekly PSI and risk-score distribution (Evidently/Grafana, as in Assignment 1); leading indicators such as the share of Tier A contacted within 7 days. When semester labels arrive, real PR-AUC and Recall@k are recomputed and compared with the validation estimates.

4. Code Quality & Documentation

20%

4.1 Code standards

  • Code style: PEP 8, enforced and formatted by ruff (line length 100; rule sets E, F, I, B, UP, D). Result: All checks passed!
  • Docstrings: Google convention on every public module, class and function, enforced by ruff's D rules.
  • Type hints: complete on parameters and return values; dataclass for experiment configs, results and settings.
  • Comments: only where intent is not obvious (e.g. why CV is computed, why a column name is stripped).
  • Tests: 6 pytest unit tests (validation rejects bad ranges, reproducible disjoint split, no sensitive features, zero-enrolment safety, top-k metrics, PSI detects shift): 6 passed. A README documents layout and commands.

4.2 Configuration

Two kinds of configuration are separated. params.yaml holds every value that affects results (seed, split ratios, feature groups, tier sizes, gates, selection rule) and is version-controlled, so a run is fully described by git commit + data hash + params.yaml. Environment variables hold infrastructure locations and secrets (tracking URI, data path, alert address); they are never committed, and only .env.example is.

6. Limitations and Next Steps

  • Proxy data. The UCI dataset (Portugal) has a 32 % dropout rate, unlike the assumed 2.7 % per semester at BTEC, and lacks weekly features. Results demonstrate the pipeline and evaluation method, not expected production performance.
  • Random split. Without enrolment dates, the stratified split may be optimistic compared with a time-based split.
  • Not yet run end-to-end in production infrastructure. DAGs load in Airflow and all task functions were executed end-to-end (4,424 students scored; 442 assigned to Tier A, 664 to Tier B), but not under a live scheduler; the Docker image was not built in this environment.
  • Next steps. Connect real exports; switch to semester-based splitting; add weekly attendance and LMS features; re-run the E02 vs. E07 comparison under the 0.02 rule.
